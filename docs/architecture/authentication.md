# Authentication boundary (Phase 1)

`GUEST` is an unauthenticated request, not a stored role. Accounts have only `USER` or `ADMIN` roles. Public information remains readable without a token; the Phase 1 demonstration routes `/api/v1/user/ping` (USER or ADMIN) and `/api/v1/admin/ping` (ADMIN only) prove the server-side policy. No flood-domain write routes exist yet. Missing/invalid JWTs receive 401, authenticated users without permission receive 403; database outages are not reported as invalid credentials.

Public registration creates USER only, normalizes email, enforces database uniqueness, and rejects unknown input fields (including `role`). Passwords are bounded to 12–128 bytes and hashed with Argon2id, with per-password random salt. Login failures for missing, disabled, and incorrect-password accounts are generic. `/auth/me` reloads the current account and exposes only ID, email, role, and creation time.

Access tokens are HS256 JWTs with `sub`, `role`, `iss`, `iat`, and `exp`, configured for 15 minutes locally. The API validates the signature, issuer, timestamps, role, and current database account/role on each protected request. They are held in web-client memory, not localStorage. Logging out revokes the current refresh session but an already issued access JWT can remain valid until expiration; disabling/changing a user invalidates it at the next request.

Refresh tokens are 32 cryptographically random bytes, sent only as host-only HttpOnly cookies scoped to `/api/v1/auth`, with configurable name, Lax/Strict SameSite, and Secure required in production. PostgreSQL stores only SHA-256 token hashes, expiry, rotation, replacement, and revocation metadata. Refresh locks the session in a transaction, inserts a replacement, and invalidates the predecessor atomically. Replay of an old token returns 401; logout revokes when identifiable and clears the cookie even without an active session. Login, refresh, and logout reject unapproved `Origin` values; without Origin, they reject `Sec-Fetch-Site` other than same-origin or none. SameSite mitigates ordinary cross-site requests. Configure exact allowed origins for non-default host ports and production TLS. Cookie endpoints without either browser header are supported for CLI clients, so do not expose the API to untrusted network clients without TLS and appropriate ingress controls.

The in-memory, per-remote-address rate limiter covers registration, login, and refresh. It does not share state across API replicas and keys the direct peer address (not untrusted forwarded headers); deploy a trusted edge limiter before exposing a multi-replica installation. The local Compose stack and its default secrets are development-only.

Admin creation is an explicit one-off command, never automatic. Set `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` in the invoking shell, then run `docker compose --profile tools run --rm -e BOOTSTRAP_ADMIN_EMAIL -e BOOTSTRAP_ADMIN_PASSWORD admin-bootstrap` after applying migrations. Repeating it for an existing ADMIN is a no-op; an existing USER with the same email is never promoted. Do not store bootstrap credentials in `.env`, commit them, or pass them as command-line arguments.

For manual Swagger testing in development, open `/docs/`, call register then login with the same email/password, and use the returned access JWT in the `Authorize` bearer control to call `/auth/me`, `/user/ping`, and `/admin/ping`. On the same origin, the browser should retain the refresh cookie; call refresh without copying a token, replace the bearer authorization with the new access JWT, then call logout. Swagger UI's cookie handling depends on the browser and origin, and a rendered browser test was unavailable in this environment; if refresh does not attach the cookie, inspect the same-origin browser request instead of weakening cookie protections. A USER must receive 403 on `/admin/ping`; create an ADMIN using the separate bootstrap command and login to verify 200. Disable Swagger in production. The cookie name in OpenAPI is the local default `fw_refresh`; change the documentation if deploying with another name.
