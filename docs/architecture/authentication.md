# Authentication boundary (Phase 1)

Google login is an optional additional identity provider using the same Flood Watch sessions and authorization checks. Password-email collisions require explicit password proof before linking, and new Google accounts are USER only. See `google-login.md` for the callback, cookie, migration, setup and operational boundaries.

Username login and real three-step password recovery require migration 14. See `password-recovery.md` for API behavior, SMTP setup, token revocation, abuse limits, compatibility, and deployment gates.

`GUEST` is an unauthenticated request, not a stored role. Accounts have only `USER` or `ADMIN` roles. Public information remains readable without a token; the Phase 1 demonstration routes `/api/v1/user/ping` (USER or ADMIN) and `/api/v1/admin/ping` (ADMIN only) prove the server-side policy. Flood-domain administration uses protected write routes. Missing/invalid JWTs receive 401, authenticated users without permission receive 403; database outages are not reported as invalid credentials.

Phase 6 report writes and personal report lists require USER or ADMIN authentication. Pending edits and uploads additionally require ownership; ADMIN review actions require the ADMIN role and self-verification is prohibited. Review requires the latest report revision to prevent publishing content changed after inspection. Public report reads expose only verified reports; unpublished reports and media are not exposed through guest routes. The UI does not substitute for these server-side checks. See `community-reports.md`.

Public registration accepts email, username, and password, creates USER only, normalizes email, enforces database uniqueness, and rejects unknown input fields (including `role`). Usernames are trimmed, lowercased ASCII letters/digits/underscores of length 3–32 with globally unique storage. Legacy and Google-only accounts retain a null username and can still use their existing email/provider. Login accepts email or username through the existing `email` field. Passwords are bounded to 12–128 UTF-8 bytes and hashed with Argon2id, with per-password random salt. Login failures for missing, disabled, and incorrect-password accounts are generic. `/auth/me` reloads the current account and exposes only ID, email, optional username, role, and creation time.

Access tokens are HS256 JWTs with `sub`, `role`, `iss`, `iat`, `exp`, and an account authentication version, configured for 15 minutes locally. The API validates the signature, issuer, timestamps, role, version, and current database account/role on each protected request. They are held in web-client memory, not localStorage. Logging out revokes the current refresh session but an already issued access JWT can remain valid until expiration; disabling/changing a user invalidates it at the next request. Password recovery increments `users.auth_version`, immediately invalidating prior access tokens, including same-second tokens. Tokens without a version remain compatible with unchanged accounts at version zero.

Refresh tokens are 32 cryptographically random bytes, sent only as host-only HttpOnly cookies scoped to `/api/v1/auth`, with configurable name, Lax/Strict SameSite, and Secure required in production. PostgreSQL stores only SHA-256 token hashes, expiry, rotation, replacement, and revocation metadata. Refresh locks the account before the session in a transaction, inserts a replacement, and invalidates the predecessor atomically. Session creation locks the account and checks its password-proof version before insertion to prevent racing old-password logins from surviving reset. Replay of an old token returns 401; logout revokes when identifiable and clears the cookie even without an active session. Login, refresh, logout, and recovery reject unapproved `Origin` values; without Origin, they reject `Sec-Fetch-Site` other than same-origin or none. SameSite mitigates ordinary cross-site requests. Configure exact allowed origins for non-default host ports and production TLS. Cookie endpoints without either browser header are supported for CLI clients, so do not expose the API to untrusted network clients without TLS and appropriate ingress controls.

The in-memory limiter keys registration, login, and refresh by direct peer address, while authenticated report create/edit/upload/review writes are keyed by account ID. It does not share state across API replicas; behind Caddy, unauthenticated auth attempts still share the proxy address, so deploy a trusted edge limiter before exposing a multi-replica installation. Public report reads do not use this direct-peer limiter. The local Compose stack and its default secrets are development-only.

Admin creation is an explicit one-off command, never automatic. Set `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` in the invoking shell, then run `docker compose --profile tools run --rm -e BOOTSTRAP_ADMIN_EMAIL -e BOOTSTRAP_ADMIN_PASSWORD admin-bootstrap` after applying migrations. Repeating it for an existing ADMIN is a no-op; an existing USER with the same email is never promoted. Do not store bootstrap credentials in `.env`, commit them, or pass them as command-line arguments.

For manual Swagger testing in development, open `/docs/`, call register then login with the same email/password, and use the returned access JWT in the `Authorize` bearer control to call `/auth/me`, `/user/ping`, and `/admin/ping`. On the same origin, the browser should retain the refresh cookie; call refresh without copying a token, replace the bearer authorization with the new access JWT, then call logout. Swagger UI's cookie handling depends on the browser and origin, and a rendered browser test was unavailable in this environment; if refresh does not attach the cookie, inspect the same-origin browser request instead of weakening cookie protections. A USER must receive 403 on `/admin/ping`; create an ADMIN using the separate bootstrap command and login to verify 200. Disable Swagger in production. The cookie name in OpenAPI is the local default `fw_refresh`; change the documentation if deploying with another name.
