# Community reports (Phase 6)

The approved October 4, 2026 Guest flow adds anonymous creation with a submitted display-name snapshot and a 15-minute report-scoped upload capability. The display name does not prove identity or ownership. The subsequently approved post-moderation flow publishes valid submissions automatically and lets ADMIN review or remove them afterward. Historical account-owned records and their protected interfaces below remain compatible. Migration 18 is documented in `guest-public-flow.md`; post-moderation requires migration 21.

Community reports are user-submitted evidence, not official flood or road classifications. Their `sourceType` is always `COMMUNITY`, including after ADMIN verification. Publication and factual review are separate: `publicationStatus` is `PUBLISHED` for `PENDING` (unreviewed) and `VERIFIED` (reviewed), and `REMOVED` for `REJECTED`. Review never certifies roads as passable or areas as safe. An empty public list is not `SAFE`. `createdAt` is submission time, not an independently verified observation time. Older submissions remain visibly old rather than evidence of current safety.

The server assigns the authenticated creator when available, `PENDING` status, and source; clients supply type, description, a manually selectable WGS84 Point (`[longitude, latitude]`), optional estimated depth in metres and the metadata described below. Valid submissions immediately become public without being marked verified. Legacy pending reports remain owner-editable. Guests cannot edit reports. ADMIN cannot verify their own report, but may remove or restore it. ADMIN may remove pending or verified reports with a nonblank reason (up to 500 Unicode code points), and restore rejected reports with a reason to `PENDING`, never directly to `VERIFIED`. Verification fields and current rejection details clear on restore. Moderation reasons and immutable history are ADMIN-only and omitted from public, creation, owner and `/reports/mine` responses.

Every moderation action uses `expectedUpdatedAt` from the latest detail. A database row lock serializes reviews with owner edits and image changes, rechecks the revision/state and records the status transition plus review history atomically. The action response captures report, images and history under that lock before commit; ADMIN detail uses a read-only repeatable-read snapshot to prevent mixed revisions. Repeated or stale actions return `409`; malformed reasons return `400`. `/admin/reports` filters `PENDING`, `VERIFIED`, or `REJECTED` with bounded pagination. ADMIN details/actions include `reviewHistory` with action, prior/new status, actor ID, reason and time; public and owner responses omit it.

The approved report form may also submit `locationName` and `locationNote` as user-supplied `COMMUNITY` metadata. The backend trims these strings and bounds them to 200 and 500 Unicode code points respectively; both remain optional for older clients and historical rows, and the backend performs no geocoding or place-name inference. Owners may update both fields while a report is `PENDING`.

The public list at `/reports` links to the dedicated anonymous creation page at `/reports/new`. Its order is display name, event type, incident map, place name, optional landmark, optional water-depth selection, description and images. New UI submissions require a trimmed place name; historical reports without one display an explicit missing-name label rather than inferred names or coordinate inputs. Public details and administrator report cards show the supplied labels.

Location access is requested only after pressing a GPS action. The map's locate control centres the blue user point and approximate accuracy circle without selecting or moving the distinct incident pin, reusing a valid shared fix younger than 60 seconds before requesting another. A separate action fetches a fresh high-accuracy position and explicitly selects it as the incident point. Manual map clicks and keyboard map-centre selection remain available without permission. Manual selection cancels pending GPS selection, late/reset/unmounted callbacks are ignored, and errors retain form drafts and the selected incident. There is no continuous location tracking or persistence of the user point. Only the selected incident coordinates are sent with the report.

The report picker shares the situation map's last center/zoom in app memory, common zoom controls and metric scale (50 m at the closest Ongkharak view). An existing report's incident location takes precedence when opening its picker. Full-map expansion keeps the same map instance and form draft, preserves geographic center on resize, traps keyboard navigation, closes with Escape or its collapse button, and restores focus. GPS cache, viewport navigation and expansion do not change report publication or add pending/rejected reports to public layers. See `map.md` for the shared navigation and progressive loading boundary.

Water-depth choices are single-select button-styled native radios: unspecified, 10 cm, 30 cm, 50 cm, 1 m or a custom centimetre value. The UI converts centimetres to the existing `estimatedWaterDepthM` contract. Unspecified omits the value and is not zero or evidence of safety; existing non-preset estimates remain editable without rounding to a preset.

Apply migration `000019_report_location_labels` after earlier migrations before releasing the matching API and frontend. It adds empty-default, bounded place metadata without inventing names for historical rows. Legacy pending-report updates that omit either label retain its existing value; explicitly sending an empty string clears it. Rolling back migration 19 permanently removes both metadata columns and their contents. Source edits do not migrate or restart the running application automatically.

Review actions require the `expectedUpdatedAt` revision from the latest detail response. Owner edits and successful media uploads advance this revision; a stale review returns 409 and must be reloaded before deciding. The UI retains the report ID when a media upload fails, retries only failed files, and never creates a second report for that retry. Uploads are not atomic across multiple files; skipping failed files leaves the already stored report and successful images intact.

Guests can list and read `PENDING` and `VERIFIED` reports and their images. `REJECTED` reports are excluded from public lists and map layers, and their direct detail/image URLs return `404` to anonymous and unrelated users. Historical owners retain private media access; ADMIN can inspect every status. Object storage remains private, and images are served through the API visibility check with `private, no-store`. Public report list/detail responses are `no-store`. Removing content cannot retract copies a visitor has already downloaded. MinIO keys are generated server-side; credentials stay on the backend, and binary data is not stored in PostgreSQL. List pagination and WGS84 viewport queries are bounded.

Image uploads still require an unexpired report-scoped guest capability and `PENDING` revision, with existing type/size/three-file limits. A report may already be public if image upload fails; the UI must state that the report exists and allow only failed-file retries without duplicate report submission. Restoration rotates the stored upload-capability hash without issuing a new token, so an old pre-removal token never becomes usable again. This preserves the migration 18 guest-capability constraint while revoking previous access.

The API refuses to start with a report-media bucket that has an anonymous bucket policy. The in-memory per-account limiter allows 10 creates, 30 edits, 30 uploads, and 30 review actions per hour. Public report reads are not limited by the API because all guests share the reverse proxy's peer address; a trusted edge limiter is required for public traffic. API limits are not shared between replicas.

The public UI and map markers label both `COMMUNITY` and verification status; they are distinct from official flood and road-condition layers. No route safety, automatic flood classification, realtime delivery, or broad ADMIN dashboard is implied by Phase 6.

Migration 21 adds public `report.updated` identifier-only change signals for creation, edits, image revision changes, removal and restoration. `report.verified` remains the separate review signal. Neither event contains private reasons, identity or removed content; clients refetch canonical public REST rather than treating an event as evidence. The verified-only public notification centre remains unchanged: automatic report publication does not send a verified notification or promote community evidence into official/AI findings. See `realtime.md`.

## Deployment and rollback

Apply `000021_report_post_moderation` after migrations 1–20 before deploying the matching API/frontend. It adds a public-read index, moderation history and a report-update outbox trigger; it does not mark existing reports verified or change their status. Existing pending submissions consequently become public under the new read policy: operators must review sensitive historical pending content before enabling it. Historical final reviews are backfilled from retained actor/time/reason with their known legacy `PENDING` prior state; no additional events or evidence are invented.

Deploy API/worker before the new frontend so `report.updated` is recognized, and retain old verification events for compatibility. Before rollback, quiesce every report creation/edit/upload/moderation write, let a compatible API dispatcher publish all queued `report.updated` rows, and confirm `SELECT count(*) FROM event_outbox WHERE event_type='report.updated' AND published_at IS NULL` is zero. Only then downgrade matching binaries and run migration 21 down while writes remain stopped. An old API rejects `report.updated` and otherwise blocks the oldest outbox row; never downgrade it before draining. Down refuses to drop the schema if those unpublished events remain and never silently discards them. Down permanently deletes moderation history and its trigger/index but retains report rows/media/current status; restored reports remain pending and become private again with the former API. Do not run down against a populated deployment without an approved backup. Source changes do not migrate or restart the running development or production application automatically.
